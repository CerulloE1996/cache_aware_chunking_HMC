# Working set of the gradient evaluation per individual

The cache-capacity lines on the chunk-count figures, and the rule which chooses the number of chunks automatically, use the working set of one gradient evaluation per individual (i.e., per row of the data, which contains all T = 6 tests), B_row:

| Implementation | B_row (bytes per individual) | How it was obtained |
| --- | ---: | --- |
| NicoStan+BayesMVP (manual gradient, `MD_BayesMVP` configurations) | 1,608 | counted from the arrays allocated for each chunk (31 T + 15 doubles) |
| Stan model (`LC_MVP_bin_PartialLog_v5_reduce_sum_static.stan`, used by `AD_Stan_tape_chunked`, `AD_Stan_WCP` and `AD_Stan_WCP_chunking`) | 19,152 | measured: memory used by the autodiff tape, its stacks and the temporary containers during one partial sum |

Both constants are set in `../R_fns_alg_paper_1_presentation_templates.R` (`paper1_bytes_per_row_BayesMVP` and `paper1_bytes_per_row_Stan`), and the chunk count at which one chunk first fits in a cache level is c* = B_row N / (cache capacity per active thread).


## NicoStan+BayesMVP: 31 T + 15 doubles per individual

Every chunk of `rows` individuals is processed with the workspace arrays resized by `resize_MVP_workspace()` in
[`inst/BayesMVP/src/MVP_functions/MVP_lp_grad_MD_AD_fns.hpp`, lines 32-80, of the BayesMVP package at the commit used for the paper](https://github.com/CerulloE1996/BayesMVP/blob/bd2221eae1782841a8a2777ed670e791785cc07c/inst/BayesMVP/src/MVP_functions/MVP_lp_grad_MD_AD_fns.hpp#L32-L80).
All are arrays of doubles:

| Arrays | Number | Doubles per individual |
| --- | ---: | ---: |
| `rows x n_tests`, one per latent class (2 classes): `Z_std_norm`, `Bound_Z`, `Bound_U_Phi_Bound_Z`, `prob`, `Phi_Z` | 5 x 2 = 10 | 10 T |
| `rows x n_tests`, shared by the classes: `y1_log_prob`, `phi_Z_recip`, `phi_Bound_Z`, `u_grad_array_CM_chunk`, `common_grad_term_1`, `y_sign_chunk_times_phi_Bound_Z_x_L_Omega_diag_recip`, `y_m_ysign_x_u_array_times_phi_Z_times_phi_Bound_Z_times_L_Omega_diag_recip`, `prob_rowwise_prod_temp`, `prob_recip_rowwise_prod_temp`, `grad_prob`, `z_grad_term`, `y_chunk`, `u_array`, `y_sign`, `y_m_y_sign_x_u`, `u_grad_array_CM_chunk_block`, `prob_recip` | 17 | 17 T |
| vectors of length `rows x n_tests`: `u_unc_vec_chunk`, `u_vec_chunk`, `du_wrt_duu_chunk`, `d_J_wrt_duu_chunk` | 4 | 4 T |
| vectors of length `rows`: `prod_container_or_inc_array`, `derivs_chain_container_vec`, `prob_rowwise_prod_temp_all`, `prob_n`, `prob_n_recip`, `log_sum_result`, `container_max_logs`, `rowwise_log_sum`, `rowwise_prod`, `rowwise_sum`, `log_lik_chunk`, `log_prev_per_obs_given_c`, `prev_per_obs_given_c` | 13 | 13 |
| `lp_array` (`rows x n_class`, 2 classes) | 1 | 2 |
| **Total** | | **31 T + 15** |

With T = 6: 201 doubles x 8 bytes = **1,608 bytes per individual**.

Not included: the per-row inputs read from outside the workspace (the `y` rows and `X` blocks, and the chunk's segment of the nuisance parameter vector), and the nuisance-gradient segment written to the output vector (a further T doubles per row). The value is therefore the working set allocated for each chunk, and the cache traffic per row is slightly larger.


## Stan model: 19,152 bytes per individual (measured)

For the Stan model, the tape is not a fixed set of arrays, so the working set of one partial sum (one chunk of `reduce_sum_static`) was measured with the probe harness in `stan/`: the model C++ generated by stanc (2.36.0, `--allow-undefined`, no optimisation flag, as in the benchmarks) with three probes added (`model_probes.diff`: before the `reduce_sum_static` call, at entry to the partial-sum functor, and at its return, i.e., after the forward pass and before the reverse sweep), evaluated exactly as BridgeStan's `log_density_gradient` does (`stan::math::gradient` on `log_prob_propto_jacobian`), single-threaded, with the Stan Math of BridgeStan 2.6.2 (Stan Math 5.0.0).
The main arena is given one large, lazily committed first block, so its use is an exact pointer difference; `malloc` is interposed (`heap_hook.c`) to record the current and peak heap; and the growth of the autodiff stacks is read from `ChainableStack`.
The data are the first n rows of the N = 50,000 dataset of the benchmarks (seed 123), passed through the pipeline's `fn_paper1_stan_data()`, with one chunk (`chunk_size = n`) for n = 500, 1,000, 2,500, 5,000, 10,000 and 20,000, plus N = 20,000 in 4 and 32 partial sums; at two parameter points (A: u ~ U(0, 1), true sensitivities, specificities, prevalence and correlations; B: all unconstrained parameters at 0), three repetitions each (the third is used).

Every component is exactly linear in the rows of the partial sum (R^2 = 1.000000; `fit_summary.txt`):

| Component (per partial sum) | Bytes per individual | Fixed (intercept) |
| --- | ---: | ---: |
| Autodiff arena (the tape): forward-pass varis, callback varis and their arena copies of operands, plus the deep copy of the chunk's `u_raw` slice (6 x 24 B) | 15,936 | 15.5 KB |
| Autodiff stacks: `var_stack_` (83 pointers per individual; the reverse sweep walks these) and `var_nochain_stack_` (206 + 6 pointers), 8 B each | 2,360 | 1.7 KB |
| Heap: peak of the Eigen local and temporary containers during the forward pass, heap owned by `chainable_alloc` objects, and the chunk's `local_sub_slice` container | 804 | 75 KB |
| Data rows read: `y` (6 doubles) and `pop` (1 int) | 52 | 0 |
| **Total** | **19,152** | 93 KB |

The intercept is mostly the 64 KB first arena block which each reducer allocates for its copies of the shared parameters (of which about 2 to 3 KB is touched); it is negligible at the chunk sizes where the L3 and L2 lines fall.
The total is 11.9 times the 1,608 bytes of NicoStan+BayesMVP: reverse-mode Stan records about 83 chaining and 212 non-chaining nodes per individual (24 B each) plus arena copies of operand values, whereas the manual gradient keeps about 201 doubles per individual and computes the adjoints analytically.

Checks:

- The paper's compiled model (`LC_MVP_bin_PartialLog_v5_reduce_sum_static_model.so`, loaded with `bridgestan`; `check_bridgestan.R`) gives the same log density and gradient norm as the harness to 10 significant figures at every point tested (e.g., N = 20,000, point A: lp = -179833.5194, |grad| = 2454.362044 in both).
- Per chunk, not per dataset: with N = 20,000 split into 4 or 32 partial sums, every partial sum has the same per-individual arena, stack and heap use as a single chunk of that size (15,939 and 15,961 B of arena per individual for blocks of 5,000 and 625 rows), and every chunk starts at the same arena address, since the nested tape is recovered and reused after each chunk.
- Parameter points A and B give identical byte counts. Forcing many rows into the tail branches (thresholds +/-2 or +/-1 instead of +/-5) lowers the arena by 3 to 9 percent.
- The tape layout is set by the Stan Math types, not the compiler; the only machine-dependent part is Eigen's allocation padding in the heap term (64-byte alignment with AVX-512 on the local-HPC, 32-byte on the laptop), about 32 B per individual (0.2 percent), so one value covers both machines.

Not included (streamed once per gradient, not reused within a chunk; about 0.5 KB per individual in total): the unconstrained parameters and their `var` copies, the `u_raw` copy in `log_prob`, the saved vari pointers and partials of the sliced terms, and the gradient output; also the shared-parameter copies (97 vars per reducer, fixed), the instruction cache and page tables.

Note that `reduce_sum_static` uses TBB's `simple_partitioner`, which halves the range until each block has at most `chunk_size = ceiling(N / N_chunks)` rows, so the realised number of partial sums is the next power of two at or above N_chunks (nominal 10, 25, 50, 100, 250 and 500 run as 16, 32, 64, 128, 256 and 512 blocks; 2 and 4 are exact). The cache lines on the Stan figures are drawn at the nominal c*; one realised block therefore fits at, or slightly to the left of, each line.
